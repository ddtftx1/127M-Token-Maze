Bug 描述

现象：在游戏进行中按 F 键打开道具面板，此时按 R 键重开一局，新一局中点击 HUD 右上角的暂停按钮（⏸）和设置按钮（⚙）持续无反应。用户以为功能坏掉了，必须按一次 ESC/P/F 键或返回主菜单再开局才能恢复。

核心状态变量：Game.itemPanelOpen（在 js/main.js 中定义，属于 Game 对象）。它表示"道具面板当前是否打开"，打开时 Game.state 应同时为 'paused'。

---

根因分析

触发链路

1. openItemPanel()（js/main.js）将 Game.itemPanelOpen 置为 true，同时将 Game.state 置为 'paused'，并隐藏 HUD、显示道具面板。
2. 用户按 R → input.onRestart → restartGame() → startGame() → buildLevel()。
3. buildLevel() 末尾执行 Game.state = 'playing';，但没有重置 Game.itemPanelOpen。同时 MG.UI.showGame() → hideAllScreens() 只是给 DOM 加 .hidden 类，不碰任何内存状态。
4. 于是新一局中 Game.itemPanelOpen === true 但 Game.state === 'playing'，这是一个非法组合（设计上 itemPanelOpen 与 state==='paused' 应成对出现）。
5. 用户点击 HUD ⏸ → hudCallbacks.onPause(false) → pauseGame(false)：

function pauseGame(openSettings) {
if (Game.state !== 'playing') { return; }   // 通过：state 是 'playing'
if (Game.itemPanelOpen) return;             // ← 卡死：itemPanelOpen 残留为 true
...
}

同理 HUD ⚙ 按钮走的是 pauseGame(true)，也被同一行守卫挡住。

为什么会导致持续失败

itemPanelOpen 只在三个地方被清零：closeItemPanel()（正常关面板）、backToMenu()（返回主菜单）、以及 input.onPause / input.onToggleItems 里按需调 closeItemPanel()。

R 键重开这条路径绕过了上述所有清零点，直达 startGame()。而 pauseGame 的守卫本身是正确的设计（道具面板真打开时点暂停应被忽略），不应修改；问题在于"新一局开始"这个节点没清掉它。

---

修复要求

主修复（必须）

文件：js/main.js
函数：startGame(diffKey, seed, isDaily)
位置：函数体的最开头，if (Game._startPending) return; 和 Game._startPending = true; 之后，var settings = MG.Settings.get(); 之前
修改内容：新增一行 Game.itemPanelOpen = false; 并附中文注释

修改后应形如（仅示意结构，具体行号以实际文件为准）：

function startGame(diffKey, seed, isDaily) {
if (Game._startPending) return;
Game._startPending = true;
// 清掉上一局残留的道具面板状态：R 键重开等路径不经过 closeItemPanel / backToMenu，
// 若不清零会让 pauseGame 的 itemPanelOpen 守卫永久拦截 HUD 暂停 / 设置按钮
Game.itemPanelOpen = false;

var settings = MG.Settings.get();
...
}

辅助修复（可选，但推荐）

文件：js/main.js
函数：buildLevel(seed)
位置：Game.state = 'playing'; 这一行的附近
修改内容：再加一次 Game.itemPanelOpen = false;

理由：startGame 是入口层，buildLevel 是"进入游戏状态"层，两层置位构成纵深防御。将来若有人在别处新增入口但忘了走 startGame，buildLevel 仍能兜底。

---

明确禁止的改动

修复过程中不要触碰以下内容，否则会引入新 bug：

1. 不要修改 pauseGame() 里的 if (Game.itemPanelOpen) return; 这一行。这是正确守卫：道具面板真打开时点暂停应被忽略。改动它会破坏"面板打开时游戏必然暂停"这个不变量。
2. 不要修改 closeItemPanel() / openItemPanel() 的现有逻辑。
3. 不要修改 MG.UI.hideAllScreens() 让它"反向清理主程序状态"。DOM 层不应该依赖游戏主流程状态，这会造成循环依赖。
4. 不要删除 backToMenu() 里已有的 if (Game.itemPanelOpen) { ... } 清理代码。虽然修复后它是冗余的，但保留无害，也是纵深防御的一部分。
5. 不要引入 ES6+ 语法（let/const/箭头函数/模板字符串/可选链等）。
6. 不要改动 Game.state 的其它赋值点。
7. 不要改 _startPending 的任何逻辑——它是防双击守卫，与本次修复无关，改动极易引入 BUG-008 类的死锁。

附：为什么只改这一处就够

· 所有开局入口（首局 / 每日挑战 / 重开 / 再玩一次 / 未来可能新增的入口）都经过 startGame()，一处覆盖全部
· 修复点位于 _startPending = true 之后、真正的开局逻辑之前，此时新一局还没开始构建，是清理遗留状态最干净、最不会与其它逻辑冲突的时机
· 只需要 1 行代码，风险极低
