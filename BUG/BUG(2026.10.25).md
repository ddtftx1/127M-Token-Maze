## BUG-001 · 指南针方向反转

- **发现日期**：2026-10-25
- **状态**：已修
- **优先级**：P0
- **模块**：`js/ui.js` → `updateHud()`
- **现象**：指南针箭头指向与终点实际方位相反。终点在右，箭头指左。
- **复现**：任意难度进入游戏 → 拾取地图 → 走到直走廊，让小地图紫色三角朝向与终点方向明显错开 90° → 观察箭头指向，与小地图终点方向相反。
- **根因分析**：`player.js` 的 `angleToEnd()` 返回 `yawTarget - yaw`，是"相对当前朝向的偏角"。`yaw` 增大实际向左转（`forward = (-sin yaw, 0, -cos yaw)`），所以相对偏角为正时终点在左侧，CSS 上应逆时针旋转，`rotate(deg)` 需取反。
- **修复**：`el['compass-arrow'].style.transform` 由 `'rotate(' + deg + 'deg)'` 改为 `'rotate(' + (-deg) + 'deg)'`。
- **校验**：直走廊中让朝向与终点方向差 90°，箭头指向小地图终点方向。
- **✅ 已修 / 2026-10-25**

## BUG-002 · 指南针形状等边对称，尖端不可辨；旋转轴心偏移

- **发现日期**：2026-10-25
- **状态**：已修
- **优先级**：P0
- **模块**：`css/style.css` `.compass-arrow`、`index.html` `#compass-arrow`
- **现象**：
  1. `▲` 字符是等边三角形，三个角完全对称，从远处看分不清尖端朝哪；
  2. `▲` 字符有基线偏移，`transform-origin` 默认在盒子中心，与视觉重心不一致 → 旋转时三角"甩"到圆环外，轨迹不是同心圆。
- **复现**：进入游戏，旋转视角持续观察指南针。尖端朝向模糊；持续旋转时三角外甩。
- **根因分析**：字符三角 + 字符基线的固有缺陷。
- **修复**（三步）：
  1. **HTML 结构**：`#compass-arrow` 由裸字符改为容器 + 内层三角
     ```html
     <div id="compass-arrow" class="compass-arrow">
       <span class="compass-needle"></span>
     </div>
     ```
  2. **CSS**：容器 14×20 + `display: flex` 居中 + `transform-origin: 50% 50%`；
     内层 `.compass-needle` 用 `clip-path: polygon(50% 0%, 0% 100%, 100% 100%)` 画尖长三角，
     `background: currentColor` 跟随主题 / 色盲模式；宽高比 1:1.7。
  3. **JS**：`updateHud()` 的 transform 仍作用在容器上，配合居中的 `transform-origin`
     使尖端描出同心圆。
  另在小屏媒体查询里按同比例缩放（11×16 / 8×13.5），保持 1:1.7 不破坏重心。
- **校验**：尖端清晰可辨；持续旋转轨迹为同心弧（不外甩）；切地牢 / 森林 / 色盲主题颜色正确跟随。
- **✅ 已修 / 2026-10-25**

## BUG-003 · 「最佳路径」不绕开终点、不捡完全场

- **发现日期**：2026-10-25
- **状态**：已修
- **优先级**：P1
- **模块**：`js/main.js` `buildBestPath()` / `autoPathCellLimit()`、`js/pathfinding.js`、`js/shop.js`
- **现象**：
  1. 靠近终点使用「最佳路径」，路径直接冲向终点，忽略周围金币；
  2. 若某金币必须踩过终点才能捡（终点是死胡同口），规划看似绕过去捡，但玩家踩终点即通关，实际捡不到；
  3. 若绕开终点也能捡，规划仍可能选"看似近但穿过终点"的路线，导致该金币漏捡。
- **复现**：简单难度，走到离终点 2–3 格处使用「最佳路径」→ 光带直冲终点，不捡附近金币。
- **根因分析**：
  - 当前语义是"最短路径 + 顺路拾取（maxDetour=4）"，不是全覆盖；
  - `findCollectTargets` 未排除"入口 = 终点"；
  - 绕行与终点判定未隔离。
- **修复**：
  1. `js/pathfinding.js` 新增导出 `buildGreedyCollectPath(maze, start, targets)`：
     从起点出发依次 A\* 到最近的未拾取目标，直到走完全部可达目标；
  2. `js/main.js` 重写 `buildBestPath()`：收集全部未拾取目标（金币 + 地图卷轴）→
     在 `try/finally` 中把终点格临时置为墙 `grid=1` → 贪心拾取 → **无论成败都还原** →
     从最后一个目标拼尾段冲终点 → 简化时把终点与全部拾取目标加入 `protectedSet`；
  3. 三种退化路径都回到旧行为（`MG.Path.findWorldPath`）：
     无目标 / 全部不可达 / 尾段不可达；
  4. `autoPathCellLimit(kind)` 改为按类型分档：fast 不限；best 中等 60 格、困难 50 格；
  5. 文案同步（启动 toast、限程停止提示、商店描述）。
- **为什么封终点**：拾取阶段把终点当墙，A\* 天然绕开。于是
  「必须踩终点才能到的金币」自动判定不可达被放弃（踩终点就赢了，实际也捡不到），
  而「绕开终点也能到的金币」会走那条更长的绕路。
- **验证**：见下方"BUG-003 专项验证"。
- **✅ 已修 / 2026-10-25**

## BUG-004 · 回放跟随视角在困难难度穿墙

- **发现日期**：2026-10-25
- **状态**：已修
- **优先级**：P1
- **模块**：`js/main.js` `updateReplay()`（`replayView === 'follow'` 分支）
- **现象**：通关后看回放，跟随视角在窄巷道中相机穿入墙内，画面变黑。
- **复现**：困难难度完整通关 → 胜利界面点"▶ 回放本局" → 幽灵穿行窄巷道时画面变黑。
- **根因分析**：相机高度固定 2.7m，困难墙高 3.5m → 相机埋在墙里；距离 3.4m 太近、`lookAt` 点 1.15m 太低，幽灵脑袋跑出画面。
- **修复**：
  - 相机距离 `camDist = 5.0`，高度 `camHeight = 4.5`（高于所有难度墙高），
    注视点 `lookHeight = 1.6`（幽灵上半身）；
  - 追加**射线兜底**：从幽灵胸口 `(pose.x, 1.5, pose.z)` 朝目标相机位射一条
    `THREE.Raycaster`，若命中 `Game.mazeView.walls`（InstancedMesh，r160 原生支持），
    则把相机沿射线拉近到 `Math.max(1.0, hits[0].distance - 0.3)` 并提前返回。
- **关键约束**：`maze.js` 天花板材质必须保持 `side: THREE.FrontSide`，
  否则 4.5m 相机会被天花板挡住。本次未改动该行。
- **校验**：困难难度窄巷道不再变黑；幽灵完整出现在画面中下部；简单/中等回放正常；
  切全景视角仍正常。
- **✅ 已修 / 2026-10-25**

- **优先级**：P2（极端场景）

- **现象**：反复领取彩蛋（每次 +99999）3 次以上后：
  - HUD "🎒道具 ×179999" 撑开按钮；

- **优先级**：P2（极端场景）

## BUG-007 · 地图卷轴可能整局不生成，玩家永远无法解锁小地图

- **发现日期**：2026-10-25
- **状态**：已修
- **优先级**：P1
- **模块**：`js/maze.js` → `pickMapSpot()`
- **现象**：极端迷宫下地图卷轴完全不出现。因为拿不到卷轴就永远解锁不了小地图，
  该局的距离提示、指南针距离、小地图全部不可用，属于"功能缺失"而非"显示异常"。
- **复现**：迷宫通路极窄 / 尺寸极小，或金币把可用通路格大量占满时。
- **根因分析**：`pickMapSpot()` 要求卷轴放在"距起点曼哈顿 ≥8 步"的通路格上，
  并避开起点/终点/金币格。原实现有 3 层兜底（≥8 步排金币 → ≥8 步含金币 → ≥4 步含金币），
  3 层全部落空时直接 `return null`。调用方 `MazeView.build()` 用 `if (mapSpot)` 判空，
  不会崩，但这一局就没有卷轴了。
- **修复**：在第 3 层之后追加第 4 层兜底——遍历**所有**通路格（含边界），
  取离起点曼哈顿距离最远者返回（仍排除起点与终点）。前 3 层的条件与优先级完全未动。
- **关键细节**：第 4 层的扫描范围必须是 `0..size-1` 而非前 3 层的 `1..size-1`。
  前 3 层的 `collect()` 只扫内部区域，若唯一可用通路格位于边界（例如 `(0,0)`），
  照抄内部范围仍会漏掉并返回 `null`——第一版实现正是踩了这个坑，测试时才发现。
- **验证**：`MG.Maze.generate` 真实难度 11/21/31 × 各 60 个种子，180 局全部生成卷轴；
  800 个随机迷宫，凡存在可选通路格必返回有效位置且不落起点/终点。
- **✅ 已修 / 2026-10-25**

## BUG-008 · 幽灵弹窗无超时兜底，会把开局流程永久卡死

- **发现日期**：2026-10-25
- **状态**：已修
- **优先级**：P0
- **模块**：`js/ui.js` → `showGhostDialog()` / `closeGhostDialog()`；`js/main.js` → `startGame()`
- **现象**：出现"发现历史挑战"弹窗时，若玩家不操作（切后台、拖走弹窗、忘了点），
  Promise 永远 pending，`Game._startPending` 永久为 `true`。此后所有 `startGame()` 调用
  都被开头的 `if (Game._startPending) return;` 静默拦截——点"开始游戏"毫无反应，
  **只能刷新页面才能恢复**。
- **复现**：同难度同种子存在历史回放且 `ghostMode === 'ask'` 时开局 → 弹窗出现后不做任何操作。
- **根因分析**：
  1. 弹窗只依赖玩家主动选择才能结束，无超时；
  2. `_startPending` 的释放挂在 Promise 上，Promise 不 settle 就永不释放。
- **修复**：
  - `ui.js` 新增 `GHOST_TIMEOUT_MS = 15000`，`showGhostDialog()` 内挂定时器，
    超时后以 `{ choice: 'solo', remember: false }` 静默关闭（不弹 toast 打扰）；
  - `closeGhostDialog()` 内 `clearTimeout` 并置空——玩家正常选择 / 点背景 / 按 ESC /
    超时四条路径都收敛到这一个函数，一处清理覆盖全部出口；
  - `main.js` 把原来的 `ghostPrompt.then(releaseStartPending, releaseStartPending)`
    双注册改为单个 `then(onOk, onErr)`，两个分支各自 `try/finally` 释放守卫；
    reject 分支显式 `proceed(false)`，保证主流程继续。
- **保持不变**：点击背景遮罩 / 按 ESC 仍等同于"独自探险"；"记住我的选择"功能未动。
- **验证**：fake timer 驱动——定时器 15000ms；超时后结果为 `solo` 且 `remember:false`；
  正常选择 / 点背景 / ESC 三条路径均清理定时器；已清理的回调不再执行；
  重复 `show` 不残留旧定时器；`main.js` 两个分支的 `finally` 均含 `releaseStartPending()`。
- **✅ 已修 / 2026-10-25**

## BUG-009 · 小地图每 120ms 全量重绘，低端机掉帧

- **发现日期**：2026-10-25
- **状态**：已修
- **优先级**：P1
- **模块**：`js/ui.js` → `drawMinimap()`
- **现象**：主循环每 120ms 调用一次 `drawMinimap()`，每次都从头遍历
  `size × size` 个格子（困难难度 31×31 = 961 格，且通路、墙各遍历一次），
  重绘已探索通路 / 已探索墙 / 金币 / 起点 / 终点 / 玩家 / 寻路路径 / 边框。
  其中大部分内容相对静止，低端手机上这个开销会带来可感知的掉帧。
- **根因分析**：完全没有缓存，静态内容与动态内容混在一起每帧重画。
- **修复**：拆成两个函数 + 一张离屏画布。
  - `drawMinimapStatic()`：背景、已探索通路、已探索墙、金币、起点 → 画进离屏 canvas
    （尺寸含 devicePixelRatio，同样 `setTransform` 做逻辑像素映射）；
  - `drawMinimap()`：判定缓存是否需要重绘 → 一次 `drawImage` 合成 → 只画动态元素
    （终点呼吸光、玩家三角、寻路路径、边框）。
- **缓存失效条件**（四类）：
  1. 玩家跨格移动（`grid.x` / `grid.y` 变化）；
  2. 探索标记数量变化（探索到新区域）；
  3. 静态签名变化：`size | theme | colorblind | minimapCoins | mapSize`；
  4. 显式调用 `invalidateMinimapCache()`。
  另导出 `resetMinimapCache()` 由 `main.js` 开局调用，避免上一局的探索计数
  让新一局误判"缓存有效"而贴出旧图。
- **保持不变**：色盲友好模式全部绘制细节（金币橙方块 / 起点蓝方块 / 终点蓝✕ /
  玩家三角白描边 + 白色小箭头）、`minimapCoins` 的实心与轮廓区分、
  两个早期 return（`minimap` 关闭、未找到地图道具）。
- **验证**：静态审查——缓存内容归属正确（`pulse` 与 `player.yaw` 确认不在缓存内，
  终点呼吸光仍是动态的）、24 种组合（三难度 × 三主题 × 色盲开关 × minimapCoins 开关）
  的绘制分支全部保留、`drawMinimap` 内已无全图遍历。
- **✅ 已修 / 2026-10-25**

## BUG-010 · 回放存储可能撑爆 localStorage 配额

- **发现日期**：2026-10-25
- **状态**：已修
- **优先级**：P1
- **模块**：`js/replay.js` → `save()` / `prune()`
- **现象**：`MAX_REPLAYS = 8`、`MAX_FRAMES = 9000`，单局回放约 200KB，8 局约 1.7MB。
  浏览器 localStorage 通常给 5MB，但隐私模式 / 旧 Safari / 部分安卓 WebView
  可能只给 2MB。原有"存不下 → prune 删最旧 → 重试一次"的兜底在
  "8 局都是近期保存的、prune 也删不动"时仍然失败，回放功能彻底不可用。
- **根因分析**：兜底只有一次，且 `prune()` 的保留条数硬编码为 `MAX_REPLAYS`，无法收紧。
- **修复**：`prune()` 增加可选参数 `keep`（默认 `MAX_REPLAYS`，排序与删除逻辑复用）；
  `save()` 在原有两次修剪之后追加**逐级减半**循环：8 → 4 → 2 → 1，
  每级减半后重试写入，全部失败才走原有的 toast 提示。
- **偏差说明**：任务书字面要求是"减半保留最近 4 条、再试一次"，但 `prune(4)`
  在现存恰好 4 条时是**空操作**，腾不出任何空间，激进修剪会完全失效。
  测试已复现该失败（配额限 4 键时只成功 4/6 次）。改为循环减半后同样场景 6/6 成功。
- **保持不变**：`MAX_FRAMES`、`SAMPLE_INTERVAL`、压缩帧格式、幽灵对战与回放读取逻辑。
- **验证**：配额 4 键 6/6 成功、配额 2 键 5/5 成功、配额 0 优雅返回 `false` 不抛错、
  正常配额行为与修改前一致。
- **✅ 已修 / 2026-10-25**

## BUG-011 · 困难难度「最佳路径」短时卡顿 100~300ms

- **发现日期**：2026-10-25
- **状态**：已修
- **优先级**：P2
- **模块**：`js/pathfinding.js` → `aStar()` / `MinHeap`
- **现象**：困难难度最多 11 个目标（10 金币 + 1 地图），`buildGreedyCollectPath()`
  会做约 `N(N+1)/2 = 66` 次 A\*。每次 A\* 都新建 3 个 `size×size` 数组
  （`gScore` / `cameFrom` / `closed`）和一个 MinHeap，困难难度每次约 10~13KB 临时分配，
  66 次约 800KB，集中在几十~几百毫秒内产生，触发 GC 造成卡顿。
- **根因分析**：每次 A\* 都重新分配工作区 + `fill()` 全表清零。
- **修复**（保守方案，只做数组复用）：
  1. 模块级复用 `_genMap` / `_gScore` / `_cameFrom` / `_closed` / `_openHeap`；
     `ensureAStarPool(size)` 只在 size 变化时重建一次；
  2. 用 generation 版本号取代 `fill()`：每次 A\* 起始 `_gen++`，
     格子首次被访问时写 `_genMap[ni] = gen` 并重置该格的 `closed/gScore/cameFrom` 陈旧值；
     判断"未访问"用 `_genMap[i] !== gen`；
  3. `MinHeap` 增加 `clear()`，复用堆实例。
- **保持不变**：A\* 算法逻辑、启发式函数、`reconstruct` 路径还原顺序、
  `buildGreedyCollectPath` 贪心策略。未引入任何新算法。
- **验证**（新旧实现逐格比对，全部 0 处不一致）：
  - 1440 组随机用例（11/21/31 三种尺寸）；
  - 同尺寸连续 500 次调用（模拟 66 次 A\* 连发）；
  - size 切换 11→31→11 共 30 轮；
  - 完整"最佳路径"路线 75 组（递归回溯生成的迷宫，11/21/31）。
- **✅ 已修 / 2026-10-25**

## BUG-012 · 道具面板状态残留导致 HUD 暂停/设置按钮失效

- **发现日期**：2026-10-25
- **状态**：已修
- **优先级**：P0
- **模块**：`js/main.js` → `startGame()`、`buildLevel()`

### 现象

游戏中按 **F** 打开道具面板后，按 **R** 重开一局，新一局里点击 HUD 右上角的
暂停按钮（⏸）和设置按钮（⚙）**持续无反应**。玩家以为功能坏了，
必须按一次 ESC / P / F 或返回主菜单重新开局才能恢复。

### 复现

1. 进入游戏（任意难度）
2. 按 **F** 打开道具面板
3. 按 **R** 重开
4. 点击 HUD 右上角 **⏸** → 无反应（预期：弹暂停菜单）
5. 点击 HUD 右上角 **⚙** → 无反应（预期：打开设置面板）

### 触发链路

1. `openItemPanel()` 将 `Game.itemPanelOpen` 置 `true`，同时把 `Game.state` 置 `'paused'`，
   并隐藏 HUD、显示道具面板。
2. 用户按 R → `input.onRestart` → `restartGame()` → `startGame()` → `buildLevel()`。
3. `buildLevel()` 末尾执行 `Game.state = 'playing';`，**但没有重置
   `Game.itemPanelOpen`**。同时 `MG.UI.showGame()` → `hideAllScreens()`
   只是给 DOM 加 `.hidden` 类，不碰任何内存状态。
4. 于是新一局中 `Game.itemPanelOpen === true` 但 `Game.state === 'playing'`，
   这是一个**非法组合**（设计上 `itemPanelOpen` 与 `state === 'paused'` 应成对出现）。
5. 用户点 HUD ⏸ → `hudCallbacks.onPause(false)` → `pauseGame(false)`：
   ```js
   function pauseGame(openSettings) {
     if (Game.state !== 'playing') { return; }   // 通过：state 是 'playing'
     if (Game.itemPanelOpen) return;             // ← 卡死：itemPanelOpen 残留为 true
     ...
   }
   ```
   同理 HUD ⚙ 走 `pauseGame(true)`，被同一行守卫挡住。

### 根因分析

`itemPanelOpen` 的清零点共四处，但 R 键重开这条路径**全部绕开**，直达 `startGame()`：

1. `closeItemPanel()`（正常关面板）
2. `backToMenu()`（返回主菜单）
3. `input.onPause` 内按需调 `closeItemPanel()`
4. `input.onToggleItems` 内按需调 `closeItemPanel()`

`pauseGame()` 里的 `if (Game.itemPanelOpen) return;` 本身是**正确设计**
（道具面板真打开时点暂停应被忽略），不应修改。
问题在于"新一局开始"这个节点没有清掉它。

### 修复

采用**两层纵深防御**，共 2 处各加 1 行代码：

**第一处（主修复）· `startGame()` 开头**

位置：`Game._startPending = true;` 之后、`var settings = MG.Settings.get();` 之前。

```js
function startGame(diffKey, seed, isDaily) {
  if (Game._startPending) return;
  Game._startPending = true;
  // 清掉上一局残留的道具面板状态：R 键重开等路径不经过 closeItemPanel / backToMenu，
  // 若不清零会让 pauseGame 的 itemPanelOpen 守卫永久拦截 HUD 暂停 / 设置按钮
  Game.itemPanelOpen = false;

  var settings = MG.Settings.get();
  ...
}
```

**第二处（辅助，纵深防御）· `buildLevel()` 末尾**

位置：`Game.state = 'playing';` 紧后面。

```js
Game.state = 'playing';
// 纵深防御：与 startGame 入口层的清理成对，保证"进入游戏状态"时
// itemPanelOpen 与 state 的不变量（面板打开 ⇔ state === 'paused'）成立
Game.itemPanelOpen = false;
Game.clock.getDelta(); // 丢弃暂停期间累积的时间
```

**为什么两层**：`startGame` 是入口层，`buildLevel` 是"进入游戏状态"层。
所有开局入口（首局 / 每日挑战 / 重开 / 再玩一次 / 未来新增）都经过 `startGame()`，
一处覆盖全部；将来若有人在别处新增入口但忘了走 `startGame`，`buildLevel` 仍能兜底。

### 明确未改动

- `pauseGame()` 的 `if (Game.itemPanelOpen) return;` 守卫 —— 保持原样；
- `openItemPanel()` / `closeItemPanel()` 的现有逻辑；
- `MG.UI.hideAllScreens()` —— 未让它反向清理主程序状态（避免 DOM 层依赖游戏状态造成循环依赖）；
- `backToMenu()` 里已有的 `if (Game.itemPanelOpen) { ... }` 清理代码 —— 虽已冗余但保留；
- `Game.state` 的其它赋值点；
- `_startPending` 的任何逻辑。

### 静态检查

`Game.itemPanelOpen` 在 `js/main.js` 共 14 处（含 2 处新增注释），按函数分布：

| 函数 | 次数 | 说明 |
|------|------|------|
| 声明（`Game` 对象字段） | 1 | `itemPanelOpen: false` |
| `startGame()` | 1 | **本次新增**，置 `false` |
| `buildLevel()` | 1 | **本次新增（辅助）**，置 `false` |
| `openItemPanel()` | 1 | 置 `true` |
| `closeItemPanel()` | 2 | 判空 + 置 `false` |
| `pauseGame()` | 1 | 守卫（未改） |
| `resumeGame()` | 1 | 守卫（未改） |
| `backToMenu()` | 2 | 判空 + 置 `false`（未改） |
| `triggerAutoPath()` | 1 | 读取（面板内允许使用道具） |
| `input.onPause` | 1 | `closeItemPanel()` 分支 |
| `input.onToggleItems` | 1 | `closeItemPanel()` 分支 |

### 验证

`node --check` 通过。另用状态机模拟脚本跑七组场景，全部通过：

|------|------|
