<h2 id="bug-023">BUG-023 · 签到自动弹窗盖住幽灵询问弹窗</h2>

- **发现日期**：2026-11-01
- **状态**：✅ 已修 / 2026-11-01
- **优先级**：P2（不崩游戏，但会让玩家刚看到的询问弹窗被顶掉，且选择结果丢失）
- **模块**：`js/checkin.js` → `otherScreenVisible()` / `scheduleAutoOpen()`

### 现象

满足"今天还没签到"且存在同难度同种子历史回放时，刷新页面后在 700ms 内点「开始游戏」：
幽灵询问弹窗（是否加载历史挑战）先出现，随后 700ms 计时到点，签到面板盖到它上面。

### 复现

1. 准备一份同难度、同种子的历史通关录像（即该种子有回放）；
2. 刷新页面回到主菜单；
3. 填入该种子，并在刷新后 700ms 内点「开始游戏」；
4. 观察：幽灵询问弹窗出现 → 700ms 后签到面板弹出并覆盖它。

### 根因分析

两点叠加：

1. `otherScreenVisible()` 的 id 名单只覆盖了商店 / 成就 / 排行榜 / 设置 / 道具面板 / 暂停 /
   胜利 / 回放条 / 验证弹窗 / 内部面板，**漏了 `ghost-modal`**；
2. 幽灵询问期间 `Game.state` 仍然是 `'menu'`（要等玩家选完、进入 `proceed()` 才变成
   `'loading'`），所以 `scheduleAutoOpen()` 里"只看 state"的判断也拦不住。

两处都没挡住，签到面板就正常弹出了。

### 修复

`js/checkin.js:731-741` —— 把 `'ghost-modal'` 加进 `otherScreenVisible()` 的名单，并注明
"它弹出时 `Game.state` 仍是 menu"这个前提：

```js
  function otherScreenVisible() {
    var ids = [
      'shop-screen', 'achievement-screen', 'ranking-screen', 'settings-panel',
      'item-panel', 'pause-menu', 'win-screen', 'replay-bar', 'secret-modal', 'dev-screen',
      // 幽灵询问弹窗也算"别的 screen"：它弹出时 Game.state 仍是 'menu'
      // （要等玩家选完才进 loading），只查 state 会把签到面板盖到它上面（BUG-023）
      'ghost-modal'
    ];
```

### 验证

- 静态：`node --check js/checkin.js` 通过；`ghost-modal` 在名单内（`grep -n "'ghost-modal'"` 命中 739 行）。
- 逻辑推演：弹窗可见 → `otherScreenVisible()` 返回 true → `scheduleAutoOpen()` 直接 return，
  不调 `openPanel()`；`autoOpened` 保持 false（本次不弹，等下次页面加载或玩家手动点按钮）。
- 人工：见文末「验证方式」第 1 条。

### 备注

- 本次选择"直接不弹"而不是"等幽灵弹窗关掉后再弹"：玩家此时已经决定开局，
  再插一个签到面板就是二次打扰；签到入口按钮一直都在，手动点即可。
- `checkin-screen` 本身不在名单里，这是故意的（它自己就是签到面板），不影响本条。

<h2 id="bug-024">BUG-024 · 签到缓存奖励只校验日期，后台状态变了仍发旧奖励</h2>

- **发现日期**：2026-11-01
- **状态**：✅ 已修 / 2026-11-01
- **优先级**：P2（需要后台状态突变才触发，属竞态；一旦触发就是"预览与实发不符"）
- **模块**：`js/checkin.js` → `claim()`

### 现象

签到面板打开期间，如果签到存档在后台被改动（多标签页操作、护符被消耗、跨过零点等），
点「领取今日奖励」时虽然会按新状态重算连签，但发出去的金币仍是"打开面板那一刻"摇出的旧奖励，
与提示里显示的连签天数对不上。

### 复现

1. 打开签到面板，停在面板上（此时已有奖励预览）；
2. 用控制台把连签改回第 1 天并清空护符，模拟后台状态突变；
3. 点面板上的「领取」：提示会按"连签重算"（如"漏签 N 天"）来写，但金币仍是旧状态那一份。

### 根因分析

`claim()` 里复用面板缓存奖励的条件只比了日期：

```js
if (view && view.day === plan.day && view.reward) reward = view.reward;
```

而奖励骰子 `rollReward(streak, isFirst)` 依赖的是**连签天数**和**奖励类型**（首签 / 常规 /
护符保住 / 断签重算）、外加 8% / 1% 的随机判定。只要 `plan.streak` 或 `plan.kind` 变了，
旧奖励就不再对应新状态。日期相同不等于状态相同。

### 修复

`js/checkin.js:378-390` —— 复用条件补上"连签天数 + 奖励类型"两项校验，任一不符就现摇：

```js
    var reward;
    var cacheOk = !!view && !!view.reward && !!view.plan &&
      view.day === plan.day &&
      view.plan.streak === plan.streak &&
      view.plan.kind === plan.kind;
    if (cacheOk) reward = view.reward;
    else reward = rollReward(plan.streak, plan.kind === 'first');
```

### 验证

- 静态：`node --check` 通过；条件四要素（view / reward / day / streak+kind）齐全，`view.plan` 为空
  时不会抛错（`!!view.plan` 短路）。
- 逻辑推演：
  - 正常路径（面板没被后台改动）：streak、kind 与打开时一致 → 仍复用缓存，**"显示即实发"不回归**；
  - 后台突变：streak 或 kind 不同 → 现摇，发奖与当前状态一致；
  - 跨零点：`view.day !== plan.day` → 现摇（原有行为不变）。
- 人工：见文末「验证方式」第 2 条。

### 备注

- 缓存的意义是"面板上看到的奖励 = 领取拿到的奖励"。状态变了以后，面板上那份本来就过期了，
  此时以新状态现摇才是正确的；面板会在领取后 `syncView()` 重建，下一次看到的就是新数据。
- 没有改奖励概率、数值与写入顺序（仍是"先落签、再发奖"）。

<h2 id="bug-025">BUG-025 · 测试模式通关后结算界面显示原难度名</h2>

- **发现日期**：2026-11-01
- **状态**：✅ 已修 / 2026-11-01
- **优先级**：P3（只影响该模式下的一处文案显示）
- **模块**：`js/main.js` → `buildLevel()`；内部模块的难度副本函数

### 现象

用测试模式（全开放空场）开局并通关后，胜利结算界面的"难度"一栏显示的是开局时选的基础难度名
（如「困难」），而不是测试模式自己的名称；局内 HUD 的难度标签同理。

### 复现

在该测试模式下开局 → 走到终点触发胜利 → 看结算界面的难度名。

### 根因分析

根因有两层，缺一不可：

1. `buildLevel()` 只把局部变量替换成测试模式的难度副本，**没有同步 `Game.diff`**；
   而 HUD（`updateHudData()`）和结算（`onVictory()`）读的都是 `Game.diff`；
2. 难度副本是 `patchDiff()` 逐字段复制的原难度对象，`name` 仍然是原难度名 —— 所以就算把
   `Game.diff` 同步过去，显示的也还是「困难」。

### 修复

1. `js/main.js:303-309` —— 该模式分支同步整份配置（HUD / 结算 / 雾浓度都读它）：

```js
    if (isSandbox) {
      diff = MG.Dev.patchDiff(diff);
      // HUD 与胜利结算读的都是 Game.diff（onVictory / updateHudData），
      // 只替换局部变量会让测试模式按原难度结算、显示成"困难"（BUG-025）
      Game.diff = diff;
    }
```

2. 内部模块的难度副本补上自己的显示名（1 行）：副本对象的 `name` 字段原来是原难度的名字，
   只同步 `Game.diff` 的话结算界面仍会显示"困难"。

### 验证

- 静态：`node --check` 两个文件均通过；`Game.diff` 赋值点在 `onVictory()` 之前
  （`buildLevel()` 在 `startGame()` 的 60ms 回调里执行，晚于 `Game.diff` 的初始赋值、早于通关）。
- 逻辑推演：
  - 通关时 `var diff = Game.diff` 拿到的是测试模式副本 → `showWin({diffName: diff.name})` 显示新模式名；
  - `diff.key` **保持不变**（没改 key），所以排行榜 / 记录 / 回放的分区键不受影响
    （且该模式本来就整段跳过写档，见上一批的 S2 防护）；
  - 下一局正常开局由 `startGame()` 重新 `Game.diff = MG.Maze.DIFFICULTIES[diffKey]` 复位，
    不会污染后续对局。
- 人工：见文末「验证方式」第 3 条。

### 备注

- 该模式不对外公开，因此本条归档采用中性措辞；代码注释里也有对应说明。
- 同步 `Game.diff` 的副作用是"顺带修正了该模式下的雾浓度来源"（`applyFog()` 也读 `Game.diff`），
  属于同一根因下的正确行为，不是新增功能。
- `diff.key` 未改是刻意的：改 key 会牵动排行榜分区、回放 key、成就判定三处，收益只是文案，
  风险不成比例。

<h2 id="bug-026">BUG-026 · `pathfinding.js` 遗留已废弃的旧路径函数</h2>

### 现象

`buildCollectPath()` 与 `findCollectTargets()` 已被 `buildGreedyCollectPath()` 取代，
全仓没有任何调用点，但函数本体与 `MG.Path` 导出仍然保留；另外 `spliceDetour()` 只被

<h2 id="bug-027">BUG-027 · 回放跟随视角每帧新建 `Raycaster`</h2>

- **发现日期**：2026-11-01
- **状态**：✅ 已修 / 2026-11-01
- **优先级**：P3（仅在回放"跟随视角"下产生，量级是每帧 1 个对象）
- **模块**：`js/main.js` → `updateReplay()`

### 现象

回放模式选「跟随视角」时，相机防穿墙的射线检测每帧都 `new THREE.Raycaster(...)`，
持续制造短命对象，给 GC 增加无谓压力（低端机上行表现为回放期间偶发掉帧）。

### 复现

进入任意回放 → 切「跟随视角」→ DevTools Performance 里看内存分配片段。

### 根因分析

`updateReplay()` 的跟随分支把射线检测器建在每帧执行路径内；而 `Raycaster` 本身无状态残留
（`set()` 会整体替换射线），完全可以复用。

### 修复

`js/main.js:70` 增加模块级变量；`js/main.js:1067-1073` 改为复用 + 每帧重置 `near/far`：

```js
  var replayRaycaster = null;

      // 复用同一个 Raycaster：three.js 的 set() 只写射线，near/far 需要每帧按需重置
      if (!replayRaycaster) replayRaycaster = new THREE.Raycaster();
      replayRaycaster.set(origin, toCam);
      replayRaycaster.near = 0;
      replayRaycaster.far = maxDist;
      var raycaster = replayRaycaster;
```

### 验证

- 静态：`node --check js/main.js` 通过；`new THREE.Raycaster` 全仓仅剩 1 处。
- 逻辑推演：`Raycaster.set(origin, direction)` 只设置射线（three r160 源码确认），
  `near` / `far` 必须显式重置，否则会沿用上一帧的值 —— 已在每帧设置，与原构造参数
  `(origin, toCam, 0, maxDist)` 等价。惰性创建也避免脚本解析期依赖 `THREE`。

### 备注

- 同分支里还有 2 个 `new THREE.Vector3`（`origin` / `targetCam`）与 1 次 `clone()`。
  它们不在本条报告范围内，且改动会扩散到相机数学，按"改动量最小"原则本轮未动；
  若要继续压榨，可下次单独做。
- 未改回放帧格式、采样间隔与播放逻辑。

<h2 id="bug-028">BUG-028 · 小地图画布不随窗口尺寸 / 横竖屏更新</h2>

- **发现日期**：2026-11-01
- **状态**：✅ 已修 / 2026-11-01
- **优先级**：P3（画面发虚，不影响功能）
- **模块**：`js/ui.js` → `init()` / `drawMinimap()`

### 现象

小地图的 `mapSize` 与画布物理像素宽高只在启动时算一次。之后窗口缩放或手机横竖屏切换，
CSS 尺寸变了但内部像素不变，画布被拉伸 → 小地图发虚（横屏短屏下 `.minimap-wrap` 的
CSS 宽度会从 168px 档变成 `min(26vh,132px)`）。

### 复现

1. 手机进入游戏并解锁小地图（或直接开该模式下用道具生成）；
2. 横竖屏切换一次；
3. 观察小地图明显发虚、格子边缘模糊。

### 根因分析

`init()` 里一次性完成 `mapSize` / `canvas.width` / `setTransform` / 离屏缓存画布尺寸的计算，
之后没有任何 resize 监听；`main.js` 的 `onResize()` 只处理了渲染器与相机。

### 修复

`js/ui.js`：

1. 模块级状态（`:42`、`:44`）：`minimapResizePending`（是否欠一次重算）、`minimapResizeTimer`（防抖 id）；
2. 新增 `resizeMinimap()`（`:149`）：按当前 `clientWidth` 与 DPR 重设主画布与离屏缓存，
   重新 `setTransform`，并 `resetMinimapCache()` 让静态缓存失效；
   容器隐藏（`clientWidth === 0`）时不按兜底值改小，而是挂起标志；
3. `init()`（`:242-251`）：绑定 `resize` 与 `orientationchange`（120ms 防抖，老 WebView 里
   横竖屏未必触发 resize，故两个都绑）；同时把 `minimapResizePending` 置 true，
   因为 init 执行时 HUD 通常还隐藏着，只能拿到兜底宽度；
4. `drawMinimap()`（`:1566`）：开头消费挂起标志，在真正可见的第一次绘制里用真实 CSS 尺寸校准。

```js
  function resizeMinimap() {
    if (!el['minimap'] || !mapCtx) return false;
    var cssW = el['minimap'].clientWidth || 0;
    if (!cssW) { minimapResizePending = true; return false; }
    var dpr = Math.min(window.devicePixelRatio || 1, 2);
    var size = Math.max(1, Math.round(cssW));
    if (size === mapSize && dpr === mapCacheDpr) { minimapResizePending = false; return true; }
    mapSize = size;
    el['minimap'].width = Math.round(mapSize * dpr);
    el['minimap'].height = Math.round(mapSize * dpr);
    mapCtx.setTransform(dpr, 0, 0, dpr, 0, 0);   // 设置 width/height 会重置变换，必须重设
    mapCacheDpr = dpr;
    if (mapCacheCanvas && mapCacheCtx) {
      mapCacheCanvas.width = Math.round(mapSize * dpr);
      mapCacheCanvas.height = Math.round(mapSize * dpr);
      mapCacheCtx.setTransform(dpr, 0, 0, dpr, 0, 0);
    }
    resetMinimapCache();   // 尺寸变了：静态缓存签名 / 坐标统计全部作废
    minimapResizePending = false;
    return true;
  }
```

### 验证

- 静态：`node --check js/ui.js` 通过；3 个新标识符都有定义；`resizeMinimap` 只在该文件内使用。
- 逻辑推演：
  - 尺寸/DPR 未变 → 直接返回，不重设画布（避免无谓的缓存重建）；
  - 尺寸变了 → 主画布 + 离屏缓存同步重设，`mapCacheSignature`（含 `mapSize`）与坐标统计被
    `resetMinimapCache()` 清空，下一次绘制必然重建静态缓存，不会出现"新尺寸配旧缓存"的错位；
  - HUD 隐藏期间收到 resize → 挂起，等首帧可见时补算，不会把画布改成兜底小尺寸；
  - 绘制逻辑仍用逻辑像素 + `setTransform`，与原有坐标体系一致。

<h2 id="bug-029">BUG-029 · 切后台再回来 3D 画面永久白屏（WebGL 上下文丢失无人接管）</h2>

- **发现日期**：2026-11-01
- **状态**：✅ 已修 / 2026-11-01（真机回归通过）
- **优先级**：P2（切后台被系统回收 GPU 上下文后必现；本局画面永久失效、只能刷新页面。不写存档、不损坏数据，但玩家看到的是"卡死/白屏"）
- **模块**：`js/main.js` → `initThree()` / `resumeGame()` / `boot()` 的 `visibilitychange`

### 现象

游戏中（任意难度、任意种子）切到后台、开别的 App 停留一段时间再切回来：按设计进入暂停菜单，
点「继续游戏」后 **3D 场景变成一片白**（画布空白），左上角出现一个类似"图片加载失败"的方块图标；
但 HUD、小地图、计时、操作全部正常 —— 甚至可以照着小地图盲走；重开本局、回主菜单再开一局
**都无法恢复**，只有刷新页面才行。

### 复现

1. 随便一个种子 / 难度进入游戏；
2. 划后台打开其他 App，停留 30 秒以上（内存紧张的中低端机更容易触发）；
3. 切回游戏 → 暂停菜单 → 点「继续游戏」；
4. 观察：3D 画面白屏 + 左上角空白方块；HUD 与小地图正常、游戏逻辑仍在跑；重开一局仍是白屏。

### 根因分析

不是贴图 / 素材加载失败，而是 **WebGL 上下文被系统回收后没有任何一层接管**：

1. 安卓在内存压力下会销毁 GPU 进程或图形上下文，画布退化成空白占位（玩家看到的就是那个"破图方块"）；
2. three.js r160 自带 `webglcontextlost` 的 `preventDefault()` 与 `webglcontextrestored` 时的 GL 重建，
   但 **`render()` 在上下文丢失时是静默 return、不抛错** —— 所以项目原有的 `try/catch` + `fatal()`
   "渲染异常"路径根本不会触发，`Game._renderStopped` 也不会置位；
3. 项目此前 **完全没监听** `webglcontextlost` / `webglcontextrestored`，三个缺口叠加：
   "丢失不暂停（玩家继续盲走）/ 恢复不重绘（浏览器恢复了也没人重新套用尺寸与像素比）/ 救不回来没出口（永久白屏零提示）"；
4. 浏览器若不派发 `webglcontextrestored`（部分内核在后台回收后不再恢复），画布就永久失效；
   而"重开一局 / 回主菜单"复用的是同一个已死的 renderer 与画布，所以怎么救都没用。

### 修复

只改 `js/main.js`（+226 行 / 12 个函数），三级兜底：

| 时机 | 动作 |
|---|---|
| **0 ms（丢失瞬间）** | `preventDefault()`（允许浏览器恢复）→ 立即暂停（`playing` / 回放都暂停，禁止盲走）→ 显示「正在恢复画面…」提示层 → 起两个兜底定时器 |
| **1200 ms** | `nudgeContextRestore()`：用 `WEBGL_lose_context.restoreContext()` 主动催一次（有些内核对后台回收的上下文不自动恢复） |
| **3500 ms** | `recreateRenderer()`：换一张新画布 + 新建 `WebGLRenderer`。场景 / 摄像机 / 迷宫 / 玩家位置都在内存里、与渲染器无关 → 直接复用，**本局进度完全不丢**；释放旧渲染器、重置阴影贴图缓存、对新画布重新挂事件、把 Pointer Lock 与 player 的画布引用指向新画布 |
| **重建也失败** | 显示「画面无法恢复」+「重新加载页面」按钮，不再白屏干瞪眼 |
| **收到 restored** | `handleContextRestored()`：重新套用尺寸 / 像素比 / 阴影 / 色调映射 → 强制渲染一帧 → 收提示 → toast「画面已恢复」 |

两处补强：

- `bindContextLoss()` 用 **画布身份守卫**：旧画布被换掉后迟到的 `webglcontextlost` 一律忽略，不会把健康的新上下文又踢进恢复流程；
- `visibilitychange` 回前台先 `isContextLostNow()` 探测再 `forceRedraw()`（有些内核对"后台回来"的画布不再参与合成，正常情况也主动重绘一帧）；
- `resumeGame()` 开头若上下文已丢，则转入恢复流程，而不是进入"看得见 HUD、看不见场景"的盲走状态。

新增函数：`setupRenderer()` / `clearCtxTimers()` / `isContextLostNow()` / `bindContextLoss()` /
`handleContextLost()` / `nudgeContextRestore()` / `handleContextRestored()` / `resetShadowMaps()` /
`recreateRenderer()` / `showContextOverlay()` / `hideContextOverlay()` / `forceRedraw()`（共 12 个）；
调用点：`initThree()`、`resumeGame()`、`boot()` 的 `visibilitychange`。

### 验证

- **桩测试**（加载真实 `js/main.js` + 最小 DOM / THREE / MG 桩）：**23/23** ——
  丢失→暂停+提示+双定时器；恢复→重绘+清定时器+收提示；永久丢失→换画布/新渲染器/旧渲染器释放/
  DOM 只留新画布/场景复用后渲染成功；旧画布迟到事件被忽略；重建失败→"重新加载"出口；
  `resumeGame` 守卫（丢失时不进 `playing`、正常时照常恢复）。
- **静态**：14 个 JS `node --check` 全过；新增代码 ES5 合规（无 `let`/`const`/箭头/模板字符串/`class`）；
  事件名 `webglcontextlost` / `webglcontextrestored`、扩展名 `WEBGL_lose_context` 拼写核对无误；
  覆盖层复用的 `.screen` / `.panel-narrow` / `.btn-row` / `.primary-btn` / `.muted` 样式均存在。
- **真机回归（2026-11-01，用户执行）**：按原路径复测（进游戏 → 切后台 30 秒以上 → 划回 →
  继续游戏），「正在恢复画面…」提示出现，几秒内自动恢复或换画布重建，本局位置与进度保留；
  连测后用户结论：「全部测试完毕，没有任何 bug…已经确定了」。
- **隔离**：本条目只改 `js/main.js`（其余 JS 的 mtime 停在上一轮），`index.html`、`css/` 一个字节没动。

### 备注

- 兜底思路是"**宁可重建也不白屏**"。本项目场景对象与渲染器完全解耦，所以重建能保住本局进度，
  才没有选择"直接提示刷新"这条更省事但更伤体验的路。
- 旧画布的迟到事件必须按身份过滤 —— 这条是唯一容易写错的地方，否则会形成"新上下文刚建好又被事件踢回去"的死循环。
- 若设备连新上下文都分配不出（极端内存不足），只给 reload 出口，不做无限重试。
- 与前六条不同：本条在修复当时**约定"真机确认后再归档"**（headless 环境验证不了 WebGL 恢复），
  所以条目落盘晚于代码；现真机已确认，补于此。
