<h2 id="bug-030">BUG-030 · Win7 下桌面退回竖屏、右侧整页滚动条、全屏图标点了没反应</h2>

- **发现日期**：2026-11-07
- **状态**：✅ 已修 / 2026-11-07
- **优先级**：P1
- **模块**：`css/style.css`（横屏媒体查询）、`js/ui.js` → `toggleFullscreen()`

### 现象

- 电脑上本应是横屏布局，实际退回竖屏口径（主菜单是窄窄一列）；
- 界面右侧出现**整页**滚动条，滚动条的样式与颜色随浏览器不同（说明是文档级滚动条，不是面板内部滚动）；
- Win7 设备点 HUD 的全屏图标（⛶）没有任何反应，也不给任何提示。

### 复现

1. Win7 + Chrome 109 打开游戏（用户确认：Win7 最后能装的 Chrome 是 **109**）；
2. 最大化浏览器（1366×768 屏、扣掉标签栏 / 地址栏 / 任务栏后视口高约 600px）；
3. 观察主菜单为竖屏口径；右侧出现整页滚动条；
4. 点全屏图标无反应。

### 根因分析

**两个独立缺陷，症状叠在一起。**

**① 桌面没有任何横屏布局分支（这是 BUG-018 修法的副作用）**

用 git 考古可以直接看清：`3ec6bcd`（跨平台兼容重构）**之前**，全站只有一条横屏查询：

```css
@media (orientation: landscape) and (max-height: 640px) {   /* 桌面与手机共用 */
```

BUG-018 的现象是「Win7 退出全屏后误入手机横屏紧凑布局 + 右侧白条」，当时的修法是给它补设备限定：

```css
@media (orientation: landscape) and (max-height: 640px) and (hover: none) and (pointer: coarse) {
```

限定确实挡住了 BUG-018 的「误入」，但副作用是**桌面从此再也进不去紧凑横屏**。
Win7 最大化时视口高约 600px（≤640），本来会命中；加了限定后 `(pointer: coarse)`
在鼠标设备上恒假，于是永远落回基础（竖屏口径）样式 —— 用户看到的就是
「电脑上又变成竖屏了」。这就是用户说的「本来电脑页面有一个专属的横屏页面」。

**② 全屏按钮"报喜不报忧"**

```js
// 修复前
var p = (elem.requestFullscreen || elem.webkitRequestFullscreen || function () {}).call(elem);
if (p && p.catch) p.catch(function () {});   // ← reject 被空 handler 吞掉
toast('已进入全屏');                          // ← 先报成功，再去试
```

三处叠加导致必然静默失败：

1. `toast('已进入全屏')` 紧跟在调用之后**无条件**执行，失败也照样提示成功；
2. promise 的 `reject` 挂的是空函数，异常被丢弃；
3. 外层 `try / catch (e) { /* 忽略 */ }` 把同步异常也吞掉。

于是浏览器拒绝进入全屏（非用户手势、策略限制、被扩展拦截等）时，
玩家看到的是「已进入全屏」这句假话 + 画面毫无变化 = 「点了没反应」。

### 修复

**① 媒体查询还原（`css/style.css`，4 处）**

```css
- @media (orientation: landscape) and (max-height: 640px) and (hover: none) and (pointer: coarse) {
+ @media (orientation: landscape) and (max-height: 720px) {
```

- 去掉 `(hover: none) and (pointer: coarse)`：按用户要求「桌面也复用手机那套紧凑横屏」；
- 门槛 640 → **720**：覆盖 Win7 + 浏览器工具栏 / 任务栏之后的常见视口高度。

**白条为什么不会复发**：BUG-018 其实是**两个**独立成因，第二个是
「Chrome 49 上 `inset:` 简写与 `env()` 失效 → `position:fixed` 容器被撑出视口」。
那部分的修复（8 处 `inset` 展开成四边 longhand + `legacy-env` / `legacy-inset` 兜底）
**原样保留**，而且 Chrome 109 原生支持 `inset`（87+）与 `env()`，根本不会失效。

**刻意保留的一处限定**：开发者面板的「左侧竖排页签」那条查询
`@media (orientation: landscape) and (hover: none) and (pointer: coarse)`
**没有**去掉。它没有高度上限，去掉会让 1920×1080 这类大屏桌面也切成
「左侧竖排页签 + 右侧内容」，反而挤掉正文宽度。项目已在该处加注释说明。

**② 全屏改成事件驱动（`js/ui.js`）**

- 新增 `fullscreenElement()` 统一判定（含 `webkit` 前缀）；
- 新增 `bindFullscreenChange()`，监听 `fullscreenchange` **与** `webkitfullscreenchange`；
- 只有事件真的到了才提示「已进入全屏 / 已退出全屏」，并用 `fsStateKnown` 给重复事件去重；
- 失败路径全部给出**可执行提示**：API 缺失 → 「当前浏览器不支持全屏」；
  `reject` / 同步异常 → 「进入全屏失败：<原因>」；900ms 后状态仍没变 → 「进入全屏失败，请按 F11」。

### 验证

- `回归/bug030-034.js`：4 条紧凑查询均已改为 `max-height:720px`；`max-height:640px` 零残留；
  紧凑查询上无设备限定；开发者面板那条限定仍为 1 处；全屏侧存在 `fullscreenchange` /
  `webkitfullscreenchange` / `请按 F11`，且旧的空 `catch` 写法已不存在。
- 全量回归 **247 项**断言全绿（run 36 + checkin 14 + robust 30 + dev-sandbox 22 + 本批 145）。
- **仍需真机**：`(pointer: coarse)` 的真实判定结果、Win7 上视口高度是否确实 ≤720、
  右侧滚动条是否消失、全屏是否能进入。无头环境验不了。

### 备注

- 若用户屏幕更高（视口 >720），仍不会进入紧凑布局；需要再抬门槛必须由用户确认，别自行改。
- 与 BUG-018 是一对：**那次是"别让桌面进"，这次是"让桌面进"**。
  将来若再有人想加设备限定，请先读这一条，别把 030 改回去。

<h2 id="bug-031">BUG-031 · 最快路径路过金币与地图卷轴时不拾取</h2>

- **发现日期**：2026-11-07
- **状态**：✅ 已修 / 2026-11-07
- **优先级**：P1
- **模块**：`js/main.js` → 主循环第 6 段（收集）/ `Game.player.onAutoFinish`

### 现象

使用「最快路径」自动寻路时，路径正好穿过金币或地图卷轴所在格，
但两者都毫无反应：金币不消失、卷轴不入库，看起来像"直接穿过了两张贴图"。

用户原话：「在使用最快路径的时候，经过金币地图时是无法［拾取］的，就像经过那个贴图一样」。

### 复现

1. 进入任意难度；
2. 购买并使用「最快路径」；
3. 让路径经过金币或地图卷轴；
4. 金币 / 卷轴既不消失也不入背包。

### 根因分析

**不是 BUG-022 复发。** 主循环第 6 段原本整段包在一个短路里：

```js
// 修复前（js/main.js:1466 附近）
var autoKind = Game.player.autoActive ? Game.player.autoKind : null;
if (autoKind !== 'fast') {           // ← "最快路径"整段收集逻辑被跳过
  var collectRadius = autoKind === 'best' ? 1.1 : 0.85;
  var got = Game.mazeView.tryCollect(...);        // 金币
  ...
  if (Game.mazeView.tryCollectMap(...)) { ... }   // 地图卷轴
}
```

原注释写得很清楚：「"最快路径"忽略沿途收集」。这是一个**设计取舍**，
但它把「不主动绕路去捡」错误地实现成了「路过也不捡」。

排除法（顺带否定两个常见推测）：

- **不是拾取窗口被跳过**：单帧位移约 0.074 世界单位（`autoSpeed = 4.4 × 1.05`），
  远小于拾取半径 0.85 / 1.2，不存在"跨过半径"；
- **不是寻路层的问题**：`BUG.md` 早前把模块写成 `pathfinding.js → buildFastPath()`，
  该函数**并不存在**；最快路径走的是 `findWorldPath`。

### 修复

把「推进」与「收集」解耦：删掉 `if (autoKind !== 'fast')` 这层短路，
收集逻辑每帧无条件执行。

- 拾取半径口径**保持不变**：`best` 用 1.1（留出路径圆角的误差余量），其余用 0.85。
  **不因为"快"而放大半径** —— 放大等于把隔壁格的东西吸过来，反而制造新的不公平。
- 「最快」的语义因此收窄为：**不主动绕路去捡目标**（目标收集在 `buildBestPath` 分支里），
  而不是"路过也不捡"。
- 顺带把 `onAutoFinish` 里"限程停下时顺手拾取"的条件从 `best` 扩展到 `best | fast`，
  保持同一口径（fast 现已不限程，此分支只是兜底）。

### 验证

- `回归/bug030-034.js`：源码里不再有 `if (autoKind !== 'fast')`（已剔除注释干扰）；
  拾取半径口径行仍在；`tryCollect` / `tryCollectMap` 两个调用都在；
  `onAutoFinish` 的 fast 分支存在。
- **BUG-022 未回归**：断言 `!Game.mapFound && ... tryCollectMap` 的可执行代码
  **不存在**（该历史说明只保留在注释里）。
- 全量回归 255 项全绿。
- **仍需真机**：用最快路径跑一局，确认金币与卷轴确实能被捡起、且不会被"吸"到隔壁格。

### 备注

- 若用户其实希望「最快路径仍完全不拾取」，这一条要回退 —— 但用户 2026-11-07 明确要求"路过了就该捡"。
- 地图卷轴被捡起后仍然只是**入背包**（库存 +1），解锁动作仍要玩家在道具面板里主动执行，
  这一点与 BUG-022 的结论一致，未改动。

<h2 id="bug-032">BUG-032 · 老内核模拟点哪个都一样、还能同时开多个</h2>

- **发现日期**：2026-11-07
- **状态**：✅ 已修 / 2026-11-07
- **优先级**：P2
- **模块**：`js/dev.js`（视觉页签）、`css/style.css`

### 现象

- 开发者选项 → 视觉 → 「老内核模拟」，点任意一个按钮，界面**看不出任何变化**；
- 再点另一个，两个可以同时挂着，不符合"通常两个会冲突"的常理；
- 用户预期：老内核模拟应当**真的降低 UI 效果**，并且能据此去别的界面体验与验收。

### 复现

1. 长按商店解锁，进入开发者选项 → 视觉页签；
2. 依次点 `legacy-env` / `legacy-inset` / `legacy-gap` / `legacy-dvh`；
3. 观察界面：几乎无变化；多个按钮可同时高亮。

### 根因分析

**这四个 class 是"能力补偿"，不是"降级预览"，所以现代浏览器上必然无感。**

`js/main.js → applyLegacyClasses()` 用 `CSS.supports()` 做能力检测，只在浏览器
**确实不支持**某项特性时才挂 class：

| class | 检测项 | 特性引入版本 | Chrome 109 |
|---|---|---|---|
| `legacy-env` | `env(safe-area-inset-*)` | Chrome 69 | ✅ 支持 → 不挂 |
| `legacy-inset` | `inset` 简写 | Chrome 87 | ✅ 支持 → 不挂 |
| `legacy-gap` | flex `gap` | Chrome 84 | ✅ 支持 → 不挂 |
| `legacy-dvh` | `100dvh` | Chrome 108 | ✅ 支持 → 不挂 |

即：**基线是 109 时，四个全部不触发**。手动点按钮强行挂上它们，效果是
"把本来就不需要的兜底规则打开一次"，于是：

- `legacy-env`：桌面没有刘海，`--safe-*` 本来就是 0px → 完全无感；
- `legacy-inset`：`style.css` 里**根本没有 `body.legacy-inset` 规则块**
  （相关定位早已全部展开成 longhand）→ 纯空转；
- `legacy-dvh`：那 4 条规则被锁在**触屏矮屏媒体查询**里 → 桌面永不命中；
- `legacy-gap`：34 条 `> * + *` margin 只作用于列表容器，开发者面板自身不在内。

至于"能同时开多个"：实现是逐个 `classList.add/remove`，**没有任何互斥逻辑**。

### 修复

把这一页从"挂补偿类"改成**真的会降低 UI 观感的模拟降级**，三档、单选互斥、全站生效。

| 档位 | body class | 降级内容 |
|---|---|---|
| 旧内核 | `sim-legacy-1` | 去 `backdrop-filter`；圆角归零；`box-shadow` 全去；面板/按钮/卡片阴影消失 |
| 更老内核 | `sim-legacy-1` + `sim-legacy-2` | 再叠加：`.screen` 去径向渐变改纯色；`.panel` 不透明 + 边框改实线灰 |
| 无硬件加速 | `sim-legacy-1` + `-2` + `sim-legacy-3` | 再叠加：`.svg-icon` 灰化降对比；面板/按钮/卡片改 2px 实线灰边；图标整体降透明度 |

实现要点：

- `js/dev.js` 新增 `SIM_CLASSES` / `SIM_LABELS` / `currentSim()` / `simIndex()` / `applySim()`；
- **三档是叠加关系**：选第 2 档会同时挂上第 1 档的 class，CSS 侧每档只写"本档新增的降级"，
  不必把前档规则复制一遍；`currentSim()` 取"最高"的那一档；
- **再点当前档位 = 取消**（单选互斥 + 开关二合一）；
- **关掉面板不清除**：这样用户可以退回主菜单 / 商店 / 排行榜 / 开局现场逐一验收
  （原本 `close()` 会调 `restoreLegacy()` 把 class 复原，本次一并移除）；
- 面板内顶部显示一条红色提示条「当前正在模拟：<档位>（仅用于测试）」；
- 刷新页面即还原（class 挂在 `body` 上，本来就不落盘）。

**明确未改动**：

- `applyLegacyClasses()` 的能力检测逻辑**原样保留** —— 它是给真老内核用的自愈机制，
  与"模拟"是两件事；
- 模拟降级**只改 CSS 观感**，不碰 `MG.Settings`、不碰 3D 场景、不写 `localStorage`。

### 验证

- `回归/bug030-034.js`：三档常量、`applySim`、叠加逻辑（`i <= upto`）、
  CSS 三档规则块、提示条样式全部存在；旧 `toggle-legacy` / `LEGACY_CLASSES` 已清除；
  `applySim` 代码段不含 `localStorage`。
- 互斥逻辑单测 4 条：选 2 档停在 2 档、同时挂 2 个 class、3 档切 1 档只剩 1 档、再点当前档取消。
- 全量回归 255 项全绿。
- **仍需真机**：三档的实际观感差异是否足够明显、降级后文字与按钮是否仍可读可点。

### 备注

- 这是本批唯一**改动面覆盖全站**的一条，回看时优先看它的 CSS 块。
- 如果将来基线真的降到 Chrome 84 以下，`legacy-*` 会自动接管，
  与 `sim-*` 互不干扰（一个在 `main.js` 检测挂载，一个只在开发者面板里手动挂）。

### 复测修订（2026-11-07 手机）

用户第一版实测提出两点，**都属实，都是本条的实现缺陷**：

1. **「有些界面仍然有圆角，比如设置界面」**
   第 1 档原先是**列举式**选择器，只写了 `.panel` / `.btn` / `.diff-card` / `.shop-card` /
   `.icon-btn` / `.dev-btn` / `.toast` / `.sign-cell` 这几类。
   设置界面里的 `input` / `select` / `.switch` / `.slider` / `.settings-scroll` 内的行与卡片
   **全都没被覆盖** —— 列举必然漏。
   **修法**：改成通配复位 `body.sim-legacy-1 *, *::before, *::after { border-radius: 0 !important }`，
   并额外显式兜住两个通配匹配不到的伪元素：`.switch::after`（开关圆钮）、
   `.slider::-webkit-slider-thumb`（滑块圆钮）。

2. **「某些按钮渲染有很大问题」**
   第 2 档原先对 `.btn` 类使用 `background-image: none !important`。
   但 `.primary-btn` / `.action-btn` 的**底色本身就是 `linear-gradient`，文字是深色 `#04121a`**
   —— 去掉渐变后 `background-color` 回落成 `transparent`，深色字压在深色界面上，
   就成了"按钮里的字看不见"的观感事故。
   **修法**：对实心强调按钮**显式赋纯色** `background: var(--accent)` 并保留 `color: #04121a`；
   `.action-btn.danger` 改实心 `var(--danger)` + 白字；
   半透明的 `.secondary-btn` / `.mini-btn` / `.icon-btn` 补 `background-color: #1e2c42`。
   **原则记下来：给元素去渐变时，必须同时给它一个不透明的底色，否则文字会失去对比度。**

<h2 id="bug-033">BUG-033 · 画质切换在 Win7 / Win10 上无效（永远高画质）</h2>

- **发现日期**：2026-11-07
- **状态**：✅ 已修 / 2026-11-07
- **优先级**：P1
- **模块**：`js/main.js`（`setupRenderer` / `onSettingChanged`）、`js/maze.js`（`MazeView`）

### 现象

在 Win7 或 Win10 的桌面浏览器里，设置中的画质切到「低 / 中 / 高」都没有任何变化，
永远是同一个观感；同样的操作在手机上有效。

### 复现

1. Win7 / Win10 桌面 Chrome 打开游戏；
2. 设置 → 画质 → 依次切「低 / 中 / 高」；
3. 画面始终不变；手机上同操作可切换。

### 根因分析

`quality` 一共影响 5 项，其中**在桌面上能看出差异的只有 1 项，而且那 1 项改不了**：

| 受影响项 | 由什么决定 | 桌面上的实际效果 |
|---|---|---|
| 抗锯齿 `antialias` | **创建 WebGL 上下文时的参数** | 唯一可见差异，但**创建后不可修改** |
| 像素比 `maxDPR` | `Math.min(devicePixelRatio, maxDPR)` | 桌面 DPR 恒为 1 → 1 / 1.5 / 2 三档**完全等价** |
| 阴影贴图尺寸 | `mapSize` 512 / 1024 | 只在初始化 `setupLights()` 时设定，**切档没重设** |
| 墙檐 | `quality !== 'low'` | 只在 `build()` 时判断，**切档没重建** |
| 终点粒子 | 60 / 140 / 220 | 只在 `build()` 时生成，**切档没重建** |

而 `onSettingChanged('quality')` 只做了两件事：

```js
applyPixelRatio();   // 桌面 DPR=1 → 空转
onResize();          // 尺寸没变 → 空转
MG.UI.toast('画质切换后建议重开一局以完全生效', 2500);
```

于是桌面上"怎么调都一样"。手机上有效，纯粹是因为 `maxDPR` 在 DPR=2/3 的设备上真的起作用。

### 修复

**① 渲染器：切档就换画布重建（`js/main.js` 新增 `rebuildRenderer()`）**

`antialias` 是创建期参数，想真正换掉只能换上下文。复用 `recreateRenderer()` 里
已经验证过的"换一张新画布 + 新 `WebGLRenderer`"手法，但去掉 WebGL 上下文丢失那套
守卫与 overlay（两者职责不同，互不干扰）：

- 新画布 `replaceChild` 就位后再释放旧渲染器，中间不留空档；
- `MG.UI.el['game-canvas']` / `Game.input.canvas` / `Game.player.canvas` 全部改指新画布
  （Pointer Lock 必须打到新画布上）；
- `resetShadowMaps()` + `bindContextLoss(newCanvas)` + 立即渲染一帧；
- 场景 / 相机 / 迷宫 / 玩家位置与渲染器无关 → **本局进度不丢**。

**② 光照与阴影贴图：新增 `applyQualityToSun()`**

`setupLights()` 只在初始化跑一次，切档时太阳强度（0.7 / 1.1）与 `mapSize`（512 / 1024）
要在这里补；`mapSize` 一旦分配就固定，必须 `dispose()` 掉 `shadow.map` 并置 `null`，
让下一次渲染按新尺寸重新分配。

**③ MazeView：就地换档，绝不重建整个迷宫（`js/maze.js` 新增 `applyQuality()`）**

只换三样能安全就地替换的：

- **墙檐**：`buildCaps()` 抽成独立方法，低档移除、中/高档补建（新增 `this.wallPositions` 缓存）；
- **终点粒子**：`buildParticles()` 抽成独立方法，按档重建 60 / 140 / 220，
  同时换掉 `pBaseY` / `pSpeed`，保证 `update()` 按下标写入不越界；
- **阴影接收**：`floor` / `walls` / `ceiling` 的 `receiveShadow` 按 `shadows && quality !== 'low'` 同步。

**为什么不能"新建一个 MazeView"来换档**：`pickCoinSpots()` 会再消费一次 `maze.rng`，
金币位置全变 —— 等于中途换了一张地图，玩家还能把已捡的币再捡一遍。
这条已写进 `applyQuality()` 的 JSDoc，防止后来者走错路。

**④ 提示语**：删掉「画质切换后建议重开一局以完全生效」，改为
「画质已切换为「低/中/高」，立即生效」；重建失败时明确告知需刷新页面。

### 验证

- `回归/bug030-034.js`：`buildCaps` / `buildParticles` / `applyQuality` / `rebuildRenderer` /
  `applyQualityToSun` 均存在；设置变更处确实调用了 `Game.mazeView.applyQuality()`；
  旧的"建议重开一局"提示已消失。
- **`applyQuality` 行为单测 12 条**（用假对象托住 THREE 依赖）：同档返回 `false` 且不重建；
  切低档返回 `true` 且重建墙檐与粒子；低档 `floor/walls/ceiling` 三者 `receiveShadow` 全为 `false`；
  高档恢复 `true`；非法档位回落 `mid`；阴影总开关关闭时任何档位都不接收阴影；
  且**不触碰 `coins`**（不会重摇位置）。
- 全量回归 255 项全绿。
- **仍需真机**：桌面三档的观感差异（抗锯齿边缘 / 阴影柔和度 / 终点粒子密度 / 墙檐有无）、
  切档后本局是否真的不丢进度、Pointer Lock 在换画布后是否仍正常。

### 备注

- 切档会重建一次 WebGL 上下文，**在低端机上有一次短暂卡顿**属预期；
- 若 `rebuildRenderer()` 失败（新上下文创建不出来，通常是显存紧张），会退化为
  "只换太阳与 MazeView"，并提示刷新页面，不会白屏；
- `recreateRenderer()`（BUG-029 的救援流程）**未做任何改动**，两套逻辑并存。

<h2 id="bug-034">BUG-034 · 开发者入口每次都要重答两题（需求）</h2>

- **发现日期**：2026-11-07
- **状态**：✅ 已实现 / 2026-11-07
- **优先级**：P2
- **类型**：需求（非缺陷）
- **模块**：`js/dev.js`、`css/style.css`

### 需求原文

> 「开发者模式答了两道题之后，是进入开发者模式，之后会在各个UI界面添加开发者选项的入口，
> 这样的话可以很方便，而不需要每次都输密码了」

用户 2026-11-07 确认：**解锁仍限本会话**，一旦刷新页面或重开游戏就失效，需要重新过口令；
且**所有界面的入口都要**。

### 原实现

- 解锁状态只存内存 `var unlocked = false`（不落盘）；
- 入口只有一个：**主菜单长按「商店」约 480ms** → 答两题 → 进面板；
- 关掉面板回主菜单后，想再进就必须重走一遍长按 + 两题。

### 实现

**① 免密入口（`js/dev.js` 新增 `mountQuickEntries()`）**

解锁成功后（`unlockAndOpen()` 内）向 **11 个界面**各挂一个低调的小按钮：

```
main-menu · pause-menu · settings-panel · win-screen
achievement-screen · ranking-screen · shop-screen
checkin-screen · item-panel · ghost-modal · hud
```

- 按钮内容是一个 `◇`，`title="开发者选项"`，`opacity: .30`，悬停才完全显现；
- 点击直接 `open()`（此时 `unlocked` 已为 `true`，不再问题目）；
- 有幂等守卫（`querySelector('.dev-quick')`），重复挂载不会叠加；
- `hud` 那一条用 `.dev-quick-hud` 变体：**底部正中**。
  原因：HUD 四角已被小地图 / 状态栏 / 摇杆 / 按钮占满，且 `#hud` 整体
  `pointer-events: none`，该变体单独 `pointer-events: auto`。

**② 解锁范围仍限本会话（未改动）**

- `unlocked` 依旧只是内存变量，**没有新增任何 `localStorage` key**；
- 刷新页面 / 重开游戏后 class 与按钮全部消失，需重新长按 + 两题。

**③ 保密口径（未改动）**

- 面板仍然「解锁才能进」，只是省掉重复答题；
- `README.md` / `CHANGELOG.md` / `THIRD_PARTY.md` **一个字都没提**（有断言把守，见验证）；
- 该条 BUG 也不进 `CHANGELOG.md` 的玩家可见条目（只在 `BUG/` 归档里留档）。

### 复测修订（2026-11-07 手机）

用户实测：「解锁之后哪怕退出去，仍然会有快捷进入，但**并没有出现**」。

**先用假 DOM 复现验证**（`/tmp/t034.js`，纯 node）：构造 11 个宿主节点 + 假 `document`，
调用 `MG.Dev.unlockAndOpen()`，结果 ——

```
创建按钮数: 11
11 个宿主上挂到入口总数: 11
没挂上的: （无）
hud 上是否有 dev-quick-hud: true
再次调用后总数（应仍为 11）: 11   ← 幂等，没重复挂
```

**结论：逻辑没问题，入口确实挂上了 —— 问题是「挂上了但看不见」。**

原样式 `width/height: 22px` + `opacity: 0.30` + `font-size: 12px` 的 `◇`，
放在手机屏幕左上角，基本等于隐形。这是我"刻意做小"的判断失误：
用户要的是**方便**，不是隐蔽到找不着。

**修法：**

| 项 | 改前 | 改后 |
|---|---|---|
| 尺寸 | 22×22 | **30×30** |
| 不透明度 | 0.30 | **0.85**（`:active` 时 1.0 + 反色） |
| 字号 | 12px | 15px |
| 描边 | `var(--panel-border)` | **`var(--accent)`**（高对比） |
| 位置 | `top/left: 6px` | `calc(6px + var(--safe-t/--l))`，避开刘海 / 圆角屏 |

**另加一道保险**：`ui.js → show()` 每次切换界面时补挂一次
（`MG.Dev.mountQuickEntries()`，未解锁直接返回、已挂则不重复）。
这样即使将来某个界面的 DOM 被重建，入口也不会丢。

> 教训：**"低调"和"看不见"是两回事**。凡是要给用户点的东西，先保证"看得见"，再谈隐蔽。
