<h2 id="bug-065">BUG-065 · 已通关后从胜利界面经开发者面板进覆盖层，返回会落到主菜单并留下僵尸对局</h2>

- **发现日期**：2026-11-13（做 BUG-064 的全量返回路径审计时发现的同族第三处）
- **状态**：✅ 已修 / 2026-11-14（口径由用户 2026-11-14 拍板）
- **优先级**：P3（仅开发者面板可达：胜利界面上也有免密入口）
- **模块**：`js/ui.js` → `backFromOverlay()` / `closeSettings()`；`js/dev.js` → `close()`
- **用户口径（2026-11-14）**：
  > 2.A 回胜利界面

### 现象 / 根因

通关后停在胜利界面（`Game.state === 'win'`，关卡**还在**、结算已出），从该界面的开发者免密入口
打开面板 → 「快速跳转」进 商店 / 排行榜 / 成就 / 签到（或「设置」），再点「返回 / 关闭」：

| 触发点 | 修复前落点 |
|---|---|
| 四条覆盖层返回（`backFromOverlay()`） | ❌ 主菜单 |
| 「快速跳转 → 设置」→ 设置里点返回（`closeSettings()` 的最终 `else`） | ❌ 主菜单 |
| 开发者面板「关闭」按钮（`close()` 的非静默分支） | ❌ 主菜单 |

后果：主菜单盖在一局 `state === 'win'` 的**僵尸对局**上 —— 关卡没释放（`mazeView` 非空），
背景仍是那一局的画面；也不会走 `MG.Dev.resetSandbox()`（沙盒测试局标记残留）。

三处都是同一个原因：**只认"暂停态"**。`backFromOverlay()` 只处理 `state === 'paused'`；
`closeSettings()` 的兜底写死 `show('main-menu')`；`dev.js` 的 `close()` 只看 `pauseResume`。
这是 BUG-056 → BUG-064 之后的**第三次**同族遗留 —— 每次都是"某个入口没有把来源传全"。

### 复现（用户路径，逐步可重复）

1. 解锁开发者选项，随便进一档难度并把角色走到终点（或按 `R` 重开后再走），进入 `win` 状态；
2. 停在胜利界面，点该界面上补挂的开发者免密入口打开面板；
3. 「环境」页 → 「快速跳转」→ 商店 / 排行榜 / 成就 / 签到（或「设置」）；
4. 点该界面的「返回」（或直接点开发者面板右上角「关闭」）；
5. **修复前**：落到主菜单，`state` 仍 `'win'`、`mazeView` 仍在、背景还是那一局；
   **修复后**：回到**胜利界面**，「再玩一次 / 看回放 / 返回主菜单」三个入口都在。

### 修复（口径 A：回胜利界面）

1. **`js/ui.js`** 新增 `isWonGame()`；`backFromOverlay()` 增加 win 分支：
   `hideAllScreens(); show('win-screen')` —— **只是把界面摆回来，不重跑 `showWin()`**，
   因此不会重复写最佳记录 / 排行榜 / 回放。
2. **`js/ui.js` 的 `closeSettings()`**：最终 `else` 由写死 `show('main-menu')` 改为调用
   `backFromOverlay()`（暂停局 → 暂停菜单，已通关 → 胜利界面，否则 → 主菜单）。
3. **`js/dev.js` 的 `close()`**：`pauseResume` 分支之后、`showMainMenu()` 之前改调
   `MG.UI.backFromOverlay()`。

三处都收敛到**同一个函数按 `Game.state` 现算**，而不是再增加一个来源标记 ——
BUG-056（设置一条）、BUG-064（四条覆盖层）、本条（win 态三处）连续三次都栽在
"逐入口传来源、漏一个就静默退化"，所以这次直接把判定收成单一事实源。

### 验证

见文末「验证汇总」。核心口径：win 态下六条返回路径全部回到 `#win-screen` 且 `state` 保持 `'win'`；
「快速跳转 → 主菜单」仍必须真正结束对局（`state === 'menu'` 且 `mazeView === null`）；
主菜单来源与暂停局来源的既有行为不得回退；**返回胜利界面不得重复结算**。

### 备注

- **为什么选 A（回胜利界面）而不是 B（直接回主菜单并释放关卡）**：这一局还没结束 ——
  玩家刚通关，胜利界面上的「再玩一次 / 看回放」是他接下来最可能点的两个按钮；
  按"返回上一层"的直觉还原到胜利界面，比替玩家决定"结束这一局"更合理。
  代价是 `state` 仍是 `'win'`、关卡不释放，但这是**安全**的：
  `win` 态下主循环只渲染、不推进任何 3D 动画、不做终点判定，不会产生后续副作用
  （BUG-066 之后 `win` 态连渲染都跳过了）。
- 与 BUG-064 的关系：同族但**不同状态**（那条是 `paused`，本条是 `win`），修法沿用同一套判定。

<h2 id="bug-066">BUG-066 · 主界面与各 UI 面板滑动卡顿，而游戏内探索迷宫流畅</h2>

- **发现日期**：2026-11-14
- **状态**：✅ 已修 / 2026-11-14
- **优先级**：P1（影响所有设备，低端机感知最强；不影响功能，但直接影响第一印象）
- **模块**：`js/main.js` → `loop()` / `loopBody()` / `isSceneCovered()` / `renderScene()`；
  `css/style.css` → `.screen` / `.screen::before` / `.sign-today::before` / 滚动容器
- **用户原话（2026-11-14）**：
  > 感觉要做几项优化，我发现部分设备它进入游戏是不卡的，但是主界面和各种UI会卡就是滑动会卡顿，
  > 那游戏内容探索迷宫就不会怎么卡

### 现象

同一台设备上：

| 场景 | 表现 |
|---|---|
| 游戏内探索迷宫（3D 画面持续变化） | 流畅 |
| 主菜单 / 商店 / 排行榜 / 成就 / 签到 等 UI 面板**上下滑动** | 卡顿、掉帧 |

这个"反过来卡"的分布本身就是关键线索：**3D 满载的场景不卡，几乎没内容的 DOM 面板反而卡**
—— 说明瓶颈不在"画得多"，而在"画了没人看的东西 + 合成层反复重算"。

### 复现

1. 打开游戏停在主菜单（或进商店 / 排行榜 / 成就 / 签到任一界面）；
2. 用手指上下滑动面板（手机上尤其明显）；
3. 观察：滑动时明显掉帧；对照进一局游戏走来走去，反而更流畅。

### 根因（三条，互相叠加）

**① 看不见的 3D 画面仍在逐帧渲染（主因）**
`js/main.js` 的 `loopBody()` 结尾是**无条件**的 `Game.renderer.render(Game.scene, Game.camera)`，
连 `Game.state === 'menu'`（主菜单 / 商店 / 排行榜 / 成就 / 签到 全屏铺满）时也照常每帧渲染一整张
玩家完全看不见的 3D 画面。更糟的是 `paused` / `win` 也一样：这两种状态下主循环**根本不推进任何
3D 动画**（只有 `playing` 会调 `player.update()` 与 `mazeView.update()`），画面是静止的，
每帧重画的都是同一张图。

**② 全屏毛玻璃挂在了滚动容器自己身上（卡顿的直接来源）**
`css/style.css` 的 `.screen` 既是全屏层、**又是滚动容器**（`overflow-y:auto` +
`-webkit-overflow-scrolling:touch`），同时挂着 `backdrop-filter: blur(2px)`。
`backdrop-filter` 模糊的是"它身后的一切"，而这层模糊结果**依附在一个正在滚动的图层上**：
手指每移动一帧，合成器都要按新的滚动偏移重新算一次**整屏**后处理。手机 GPU 的填充率本来就被
3D 画布吃掉大半 → "画布不动时还凑合，一滑面板就卡"。
（游戏内 `/` 只有 `.stat` / `.icon-btn` 这类几十像素的小芯片带 blur(6px)，代价可忽略 ——
这正是"游戏内不卡"的原因。）

**③ 无限循环的 paint 动画 + 双层滚动抢手势（加剧）**
- `.sign-today { animation: signBreathe }` 动画的是 **`box-shadow`**（10↔20px 模糊）→
  **paint 动画**，无限循环、每帧重绘，且它就在带全屏毛玻璃的 `.screen` 里；
- `.screen`（外层）套 `.panel` / `.settings-scroll` 等（内层）**双层滚动**，没做滚动链隔离，
  触屏上内层滚到边界会把剩余手势传给外层 —— 体感是"滑到头突然跳一截"，
  玩家通常也会描述成"卡"。

### 修复

**① 菜单/暂停/胜利态改为"脏标记按需渲染"**（`js/main.js`）

- 新增 `isSceneCovered()`：`Game.state` 为 `menu` / `paused` / `win`，或开发者面板打开时 → 画面被全屏层盖住；
- 新增 `renderScene()` / `markSceneDirty()`：需要时渲染一帧并清脏标记；
- `loopBody()` 结尾改为"盖住且没脏 → 跳过渲染"；`loading` / `playing` / `replay` **保持每帧渲染**；
- 置脏的四处（缺一处就会"画面停在旧的"）：`backToMenu()`（关卡已释放、背景色已换，必须重画）、
  `onResize()`（`setSize` 会重设画布）、`onSettingChanged()`（主题/雾/阴影/画质/色盲都会改 3D）、
  `rebuildRenderer()` 本身自带首帧渲染（无需额外置脏）；
- 另在 `pauseGame()` / `onVictory()` 各置一次脏，保证画布停在"按下暂停 / 刚抵达终点"的**准确一帧**，
  而不是上一帧。

**② 毛玻璃从滚动容器挪到固定不动的独立层**（`css/style.css`）

- `.screen` 删掉自身的 `backdrop-filter` 与 `-webkit-backdrop-filter`（**两条都删**，
  只删无前缀那条等于白改 —— Chrome 认前缀），`radial-gradient` 背景原样保留；
- 新增 `.screen::before { position: fixed; inset:0; backdrop-filter: blur(2px); pointer-events:none; z-index:-1 }`：
  这一层锚在视口上、滚动时纹丝不动，身后底图在滑动期间没有变化 → 模糊结果可被缓存成纹理，
  滚动只做混合。2px 模糊强度原样保留；
- 补 `isolation: isolate` 把 `.screen` 钉成层叠上下文，让 `z-index:-1` 稳定落在"背景之上、内容之下"；
- `blur(6px)` 的 6 个 HUD 芯片（`.stat` / `.icon-btn` / `.compass-ring` / `#minimap` /
  `.minimap-lock` / `.replay-bar`）**一行未动**（游戏内本来就不卡）。

**③ 呼吸动画改合成器属性 + 滚动链隔离**（`css/style.css`）

- 光晕移到 `.sign-today::before`，`@keyframes signBreathe` 只动 `opacity` ——
  动画期间只有合成，不再每帧重绘 box-shadow；`prefers-reduced-motion` 段同步补上该伪元素；
- 11 处滚动容器加 `overscroll-behavior: contain`，手势只驱动当前这一层。

### 验证

见文末「验证汇总」。核心口径：**菜单/暂停/胜利/开发者面板态静止期渲染次数 ≈ 0，
必须画的时机（回菜单、resize、切主题、切画质、进入暂停、通关）各保留 1 次**，
`playing` / `replay` 不受影响；BUG-064 的 264 条断言无回退。

### 备注

- **一条重要的取舍**：`paused` / `win` 也纳入了"跳过渲染"。理由是这两种状态下主循环本来就不推进
  任何 3D 动画，画面静止 —— 每帧重画同一张图玩家一点也看不出来，却让画布上的全屏毛玻璃每帧重算。
  风险是"以后若给暂停态加了 3D 动效（例如暂停时让粒子继续飘），必须同步删掉它的 covered 判定"，
  已写进 `isSceneCovered()` 的注释。
- **一条反向约束**：以后谁给 `#app` / `.screen` 加 `transform` / `filter` / `will-change` /
  `contain:paint`，`.screen::before` 的 `position:fixed` 会立刻错位（变成跟着面板滚），
  必须回头改成绝对定位铺满 —— 已写进 CSS 注释，别无声无息地加。
- **唯一可见变化**：签到「今天」格子的外发光颜色由写死的科技蓝 `rgba(53,208,255,…)` 改为
  `var(--accent)`。科技主题下像素级一致；地牢/森林主题下原本是"橙色边框配蓝色光晕"的错色，
  现在各自发光。呼吸节奏仍是 2.4s ease-in-out，外发光半径固定 16px、只变强弱
  （原来 10↔20px 会胀缩）—— 因为 box-shadow 动画本身就是要消掉的那个开销。
  若不接受这处颜色变化，改回写死蓝色即可（一行）。
- 本缺陷**不改任何视觉结构、不改任何功能逻辑、不碰存档格式**。

<h2 id="bug-067">BUG-067 · 终点永远固定在右下角（`farCell` 是死逻辑），可被推算速通</h2>

- **发现日期**：2026-11-14（用户反馈）
- **状态**：✅ 已修 / 2026-11-14（口径由用户拍板）
- **优先级**：P1（关卡设计缺陷：直接架空"探索迷宫"的核心玩法，且影响所有难度）
- **模块**：`js/maze.js` → `pickEndpoints()` / `DIFFICULTIES`；`js/replay.js` → 布局版本
- **用户原话（2026-11-14）**：
  > 我们需要一个比较特殊的终点设计，我曾经把它交给我一个朋友玩，他说因为终点永远都是在右下角，
  > 所以说只要我稍微推算一下，我目前走到了哪里，那么我就可以轻轻松松速通，
  > 所以说我认为终点的设计不可能一直仅次于一个位置

### 现象

终点位置是**常量**。用真实生成器实测（每档 200 局，DFS / Prim 各半）：

| 难度 | 终点位置 | 唯一终点数 | 落在右下 3×3 区域 |
|---|---|---|---|
| 简单 11×11 | **100% `(9,9)`** | **1** | 100% |
| 中等 21×21 | **100% `(19,19)`** | **1** | 100% |
| 困难 31×31 | **100% `(29,29)`** | **1** | 100% |

后果：玩家一旦知道"终点永远在右下角"，就只要判断自己在迷宫的哪个方位、然后一路往东南偏着走，
不需要探索。用户的反馈正是他朋友试玩后给出的速通法。

顺带说明：游戏本身设计了"**先找到地图卷轴 → 才能在道具面板主动使用、解锁小地图与指南针**"，
策划意图就是让玩家在拿到地图前**不知道终点方向**。固定角落把这条设计彻底架空了。

### 根因

`js/maze.js` 的 `pickEndpoints()`：

1. `end` 默认就写成 `{ x: size - 2, y: size - 2 }`（右下角）；
2. `farCell === true` 时（中等 / 困难）改成"在通路格里挑**曼哈顿距离**最远的"，
   而曼哈顿距离 `|x-1| + |y-1|` 在 `(size-2, size-2)` 取到**唯一最大值** ——
   循环又从 `y = 1` 升序扫描、用严格大于 `d > bestD` 保留下来的必然是那个角。
   于是这个分支**永远返回右下角**：`farCell` 这个难度开关实际上**完全没有生效**（死逻辑）。
3. `x + y > size * 0.5` 那个约束同样形同虚设（角落天然满足）。

也就是说：不是"终点设计得不好"，而是**这一整段分支是废码**。

### 复现

1. 随便开三档难度各若干局（或用 `MG.Maze.generate(seed)` + `MG.Maze.pickEndpoints(maze, diff.farCell)`
   直接复算，不需要真机）；
2. 统计 `maze.end`：修复前 100% 是 `(size-2, size-2)`；修复后应为散布在远端的多个格子。

### 修复（用户口径：随机于"路径距离 ≥ 80% 最远"的通路格）

**`js/maze.js`**：

1. 新增 `bfsSteps()`：从起点做一次 BFS，得到每个通路格的**真实路径步数**
   （旧实现用曼哈顿近似，在迷宫里根本不成立 —— 两格可能只隔一堵墙却要绕十几步）。
   自带最小实现而非调用 `MG.Path.bfs`，因为加载顺序是 `maze.js → pathfinding.js`，不能反向依赖。
2. 重写 `pickEndpoints(maze, farRatio)`：
   - 候选 = 路径步数 ≥ `ratio × 本局最远路径步数` 的**单元格中心**（奇数坐标，与旧口径一致）；
     可达性由 BFS 天然保证（不可达格 `dist = -1` 自动被排除）；
   - 用**由 seed 派生的独立随机流**（`mulberry32(hashString(seed + '#end'))`）挑选，
     保证同 seed 恒得同一终点（每日挑战世界同步、幽灵/回放可复现），
     且**不消费 `maze.rng`**（金币/卷轴是在 `MazeView.build()` 里接着它抽的）；
   - 先在该随机流下**在非空象限里等概率挑一个象限**、再在象限内均匀取一格：
     远端格子天然集中在东南，全局均匀取会让东南占约 38%，分层后四个象限大致均衡。
3. `DIFFICULTIES` 的 `farCell` 字段改为 **`endFarRatio: 0.8`**（各档一致；未来难度可单独调）。

**`js/replay.js`（用户口径：旧回放自动失效）**：

4. 新增 `MG.Maze.LAYOUT_VERSION = 2`（关卡布局规则一变就 +1）；
5. 回放存盘 payload 增加 `layout` 字段；读取时版本不符 → 返回 `null` **并删除该键**
   （抽出 `readValid()` 供 `load()` / `loadFull()` 共用）；`prune()` 顺带清掉版本不符的记录，
   不让它们白占配额。这样"幽灵跑向一个已经不存在的终点"不会出现。

**`js/main.js` / `js/dev.js`**：调用点改为 `diff.endFarRatio`；沙盒 `patchDiff` 置 `endFarRatio = 0`
（沙盒稍后由 `prepareMaze()` 直接接管 start/end）。

### 备注

- **为什么不用"记住上一局象限"**：那要求记住玩家历史，同 seed 的布局就会因人而异，
  直接破坏"同 seed 同布局"（每日挑战世界同步、幽灵与回放都依赖它）。
  改用 seed 派生象限后，既不可预测、又完全确定 —— 这也是实现时对用户口径的一处**有意偏离**，
  已向用户说明。
- **金币 / 卷轴位置会变（别误解成 bug）**：独立随机流只保证"随机序列没有被这次改动多推进"，
  但 `pickCoinSpots` / `pickMapSpot` 都会把**终点格排除出候选集合**，终点一变、候选集合差一格，
  洗牌结果整体不同。实测同 seed 下会有 1~3 枚金币换位。这属于"关卡布局变化"的一部分，
  已被 `LAYOUT_VERSION` 统一作废旧回放。
- **排行榜 / 最佳记录未做版本化**：新规则的终点平均在"89~90% 最远"处，比旧的"100% 最远（角落）"
  略近，历史成绩的可比性有约 10% 的偏差。考虑到这是本地记录、且成绩仍是玩家自己跑出来的，
  本次**不重置**；如果要求严格可比，说一声即可加版本化并清空。
- `fast_simple`（简单 ≤40s）成就阈值未调整，但新规则下简单档路径平均为最远的 90%，
  与旧规则（100%）接近，暂按不变处理；真机复测若明显偏松再调。
